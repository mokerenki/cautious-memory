# Vulnerability Multi-Traffic Evidence

The vulnerability detail's "Related Traffic" supports cross-page multi-select, purpose and note, sorting, and unbinding. The traffic page can also multi-select records and associate them with one existing vulnerability at a time. Traffic evidence inherited by a task is read-only, and modification requires entering the source task.

The "Agent Auto-Bind Traffic" in system settings is off by default, and the read and modify interface is `/api/settings`'s `agent_traffic_binding`. Enabling it increases the token consumption of reading request/responses, tool calls, and prompts; the next round of the Agent uses the new setting. When off, the auto-binding parameter and rebinding tool are hidden, no auto-binding guidance is injected, and newly submitted auto-binding from an already-running session is rejected. Manual binding, traffic capture, reading saved evidence, and export are unaffected.

When enabled, the default flow is "discovery stored → auto-trigger the report Agent → verify and bind traffic → write the report by the latest evidence version". The reporter retains the verification command, key output, existing real traffic IDs, and purpose in `evidence`; the report Agent combines the vulnerability details and execution records, verifies with `traffic_search` / `traffic_get`, then calls `bind_finding_traffic`, and then reads the latest `version` to save the report. When the switch is off, the report Agent does not additionally get the raw traffic search/read tools and does not auto-bind; it can still read manually bound snapshots and generate a report.

Compatible with existing callers: `report_finding`'s `traffic_refs` / `evidence_hint_id` can still bind immediately and explicitly. Binding is optional: for non-HTTP vulnerabilities such as TCP, or when nothing is captured or the exact record cannot be found, omitting the references still allows normal reporting and writing the report; retain other verifiable evidence such as command output and logs, and it is recommended to explain the reason for not binding; no new required fields are added. The submitted IDs must all be valid with complete bodies. Any single failure rolls back this binding operation; when binding with the submission fails, the whole report is rolled back. Repeatedly appending the same snapshot does not increase the binding and does not overwrite the note.

## Agent IDs and Report Versions

`report_finding` adds an optional parameter, and the array order is the initial evidence order:

```json
{
  "traffic_refs": [
    {"traffic_id": "真实流量ID", "role": "baseline", "note": "正常账户请求"},
    {"traffic_id": "另一个真实流量ID", "role": "proof", "note": "复现请求"}
  ]
}
```

The purposes are `baseline` (normal control), `proof` (vulnerability proof), `verification` (supplementary verification), and `supporting` (supporting evidence, default). First verify real records with `traffic_search` / `traffic_get`; the domain and time are only used for candidate filtering and do not presume task ownership.

The prompt reference is [CyberStrikeAI's vulnerability reporting tool guidance](https://github.com/RuoJi6/CyberStrikeAI/blob/54d56774b8bd285817d16d48b70a4a5e6e0963f7/internal/app/vulnerability_tools.go), combined with this project's optional binding convention, without introducing the mandatory no-package reason validation. Do not guess IDs, and do not repeatedly probe only to complete a package.

The first returned line is still `finding recorded: <exploration node ID>`; the subsequent JSON provides the independent vulnerability record `finding_id`, the exploration node `finding_node_id`, and the binding summary.

- `get_finding_traffic(finding_id)` uses the **independent vulnerability record ID** and returns an ordered list and `version`; passing `binding_id`, `side=request|response`, `offset`, and `length` reads in segments, at most 8192 bytes per segment.
- `update_finding_report`'s `finding_id` **continues to use the exploration node ID**. A new `evidence_version` fills in the actually read version; evidence changing during generation will reject writing the old version, and it must be re-read and regenerated.
- When an old report call does not pass a version, it does not claim to override existing traffic evidence. After binding, note, purpose, or sort changes, an existing report prompts that it needs updating.

After enabling auto-binding, `add_hint` / `add_task_hint` support saving `traffic_refs` in a single hint or in each element of a batch `hints`. When the Planner reports on behalf, it can pass `evidence_hint_id`, explicitly selecting references from the corresponding hint in this task; it cannot reference inherited hints. The system does not guess bindings by domain, time, or browsing history. A failed submission does not generate a partial vulnerability or trigger the report early.

When an existing vulnerability is missing a binding, `bind_finding_traffic(finding_id, traffic_refs)` can be used to supplement it, without re-registering. `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` return explicit `finding_id` and `finding_node_id`; the old `id` keeps the exploration node semantics.

At startup, only optional properties are added to the old tool schema, the original default traffic tool binding is extended to the report Agent, and the rebinding tool is given to the report Agent by default. Custom binding lists, prompts, descriptions, and enable status are preserved. Guidance is uniformly added after the final tool assembly: the reporter role is responsible for handing over existing evidence, and the report Agent is responsible for verifying, binding, and writing the report. A platform conversation lacking task context should hand off to the task Agent via a structured prompt rather than reporting directly. Before judging a task complete, it should first hand off existing evidence; a missing package does not force waiting. A failed `report_finding` does not trigger the report Agent.

## API

Base path: `/api/exploration/findings/{finding_id}/traffic`, using the independent vulnerability ID. Reuses authentication; `context_task` validates task visibility and inherited read-only.

| Method / Relative Path | Request / Return |
| --- | --- |
| `GET` | Ordered summary, evidence version, report adopted version |
| `POST` | `{"traffic_refs":[...]}` batch append |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |
| `DELETE /{binding_id}` | `{"version":1}` |
| `PUT /order` | `{"version":1,"binding_ids":["2","1"]}`, must be the complete list |
| `GET /{binding_id}` | Snapshot metadata and a bounded body preview |
| `GET /{binding_id}/body` | `side`, `offset`, `length`; `download=1` downloads the full original bytes |

Version/sort collection conflicts or writes during archiving return `409`; inherited writes return `403`; a binding that does not exist or does not belong to the vulnerability returns `404`; traffic/attachment read and validation failures clearly return an error.

## Storage and Migration

Startup idempotent migration of PostgreSQL: adds `traffic_evidence_snapshots`, `finding_traffic_bindings`, and `findings.evidence_version` / `report_evidence_version` (default 0). Does not guess supplementary bindings from historical text.

The snapshot stores the original traffic ID, capture time, URL, method, status, request/response headers, body length, and SHA-256. The body is stored by hash at `<data>/evidence/blobs/<first two chars>/<hash>.bin`, independent of the cleanable `data/traffic`, and multiple vulnerabilities can share snapshots/bodies. Snapshots provide no content update interface; on a checksum mismatch, reads and exports fail.

The full body is read under the original traffic write lock, including large-body blobs and old directory records. The file is first persisted and validated, then written into the exploration node, intent relationships, vulnerability, snapshot, and binding with a single PostgreSQL transaction; the planner is notified only after the commit. A failure may leave an unreferenced file but does not produce a partial business record.

The PostgreSQL advisory lock `7337741004` coordinates evidence files and SQL references; the task row lock forbids evidence modification after archiving is queued. Recovery keeps the evidence lock throughout from body installation to metadata commit. Deleting a vulnerability cascades to remove bindings.

The cleaner runs hourly and only reclaims content that is unreferenced and not part of an in-progress operation, with at least a 24-hour delay. Normal traffic cleanup does not touch the evidence directory. When backing up hot data, back up both PostgreSQL and `data/evidence`.

## Export and Archiving

Markdown includes an ordered evidence list and version; JSON includes metadata; CSV adds the count and binding IDs. `md-zip` keeps the vulnerability Markdown and provides:

```text
evidence/<finding_id>/<binding_id>/
  manifest.json
  request.http
  response.http
  request.bin
  response.bin
```

Markdown references the packets via relative links. Before sending the download, attachment copying, checksum validation, compression, disk sync, and CRC read validation of all ZIP entries are completed; a missing/corrupt file makes the whole download fail. Complete attachments keep the original binary bytes.

Archive v3 collects snapshots and bodies by vulnerability binding relationships, not depending on original traffic or domains. Hot data is cleaned only after the package validation completes; shared evidence is retained. Recovery first validates and installs the body, then transactionally restores metadata and bindings, supporting failure retry. v1/v2 remain recoverable, and missing new fields are explicitly filled with 0.

## Validation and Boundaries

Set an independent, newly created PostgreSQL test database for each test package, specified via `ARTEX_PG_DSN`, avoiding residual task/model fixtures triggering background runs. Run the complete tests of the relevant packages and confirm there are no skips caused by missing configuration:

```sh
# Set ARTEX_PG_DSN to the corresponding independent test database before running each package; an explicit configuration failure must error.
go test ./<package> -count=1
go test -race -p 1 ./evidence ./db ./agent ./server -run 'TestEvidence|TestFindingTraffic|TestFindingEvidence|TestReportFindingAtomicContract|TestTaskArchive'
```

Frontend validation includes `npx tsc --noEmit`, Biome checks of affected files, a Webpack build, and a `NEXT_EXPORT=1` static export. Use an independent cache directory to avoid overwriting a running dev service.

Local end-to-end acceptance uses an independent port, a controlled HTTP / domain HTTPS target, and a temporary data directory, covering the two binding entry points, cross-page selection, sort/note, error prompts, inherited read-only, download, and exporting, archiving, reclaiming hot bodies, restoring and validating the hash after deleting the original traffic.

The first version uses a global evidence coordination lock; during large-batch binding/export or slow attachment downloads, other evidence operations may wait. When recording records or complete bodies are missing, evidence cannot be fabricated. This feature does not change the capture toggle and does not handle the certificate issue of accessing an IP directly over HTTPS.
